Conclusion

Real overlap is present, but this experiment does not establish a build-latency win from adding workers. Two workers changed the clean-build median by +0.8% and the edited-build median by +13.3% relative to one worker. The recorded Cargo/idle-observation/drain sequence median fell from 218.26s to 214.12s (1.9%), showing that some benefit can occur outside Cargo's timed interval. Four workers made clean builds slower in both rounds.

More workers completed more seals, canceled more candidates, and accumulated more catalog-permit wait time in both rounds. That supports reducing repeated work and serialized catalog setup before increasing worker count further; it does not quantify how much of the elapsed-time difference each cause explains. The small sample and shared node also limit conclusions about the noisy edited builds.

This executable predates the native-state cache and batched identity allocation. Their performance is not represented here. The two-worker default remains provisional while those separately queued comparisons run.

What differs

All SL7 cases use the same executable. SL7_SEAL_WORKERS selects one, two, or four independently connected workers. Preparation and retirement can overlap across files; durable catalog commits remain serialized. Per-inode gates prevent overlapping candidates for one file, and duplicate chunks are resolved at publication.
